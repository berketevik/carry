# C05: proposals, review and targeted corrections

Implemented locally on 2026-09-10. C04 capture is retained. MCP can optionally
submit decision drafts; acceptance and rejection remain explicit CLI operations.
The full app UI is C06.

## Propose and review

A client model or a person supplies the synthesized decision text. Carry does
not call a separate model or silently turn a prompt into an accepted fact.

```sh
carry --workspace /path/to/state proposal add --event decision-1 \
  --source records --title 'Cedar delivery' \
  --content 'Cedar pilot delivery is October 15, 2026.'
carry --workspace /path/to/state proposal list
carry --workspace /path/to/state proposal show --id rec_ID
```

`show` returns the content, source links, target snapshot, unified diff, current
revision and a `review_token`. Inspect the diff, then pass that exact token:

```sh
carry --workspace /path/to/state proposal accept --id rec_ID \
  --expect-revision 1 --review-token TOKEN_FROM_SHOW
# Or retain the proposal as rejected:
carry --workspace /path/to/state proposal reject --id rec_ID \
  --expect-revision 1 --review-token TOKEN_FROM_SHOW
```

Acceptance rebuilds the index. If rebuilding fails, the decision remains
accepted and the command returns `accepted_index_pending` with the actual index
failure and a nonzero exit code. `carry index` or an exact acceptance retry
finishes indexing without accepting twice. CLI `proposal list --all` shows
reviewed records as well as pending proposals, with source paths and timestamps.

A captured event already owns a draft. Refine that draft by using its receipt's
`event_id` and `proposal_revision`:

```sh
carry --workspace /path/to/state proposal add --event evt_EVENT_HASH \
  --source records --expect-revision 1 --title 'Cedar delivery' \
  --content 'Cedar pilot delivery is October 15, 2026.'
```

Use the receipt for the specific event being synthesized. The last receipt in
status is not a session selector when several sessions are running concurrently.
The record ID and raw-event source link are retained. The previous draft text is
archived in `<records_dir>/.history/`; raw-event Markdown is never rewritten.
The draft revision increases, so obtain a new token with `proposal show` before
acceptance. Exact retries return the existing proposal. Different events with
identical wording stay distinct. A synthesized/reviewed event cannot be silently
replaced by a different retry.

## Correct an existing record

A correction names its target and expected target revision. It may target either
a Carry record or an imported Markdown record from any configured source.

```sh
carry --workspace /path/to/state proposal add --event correction-1 \
  --source records --title 'Cedar revised delivery' \
  --target rec_TARGET --target-source records --expect-target-revision 1 \
  --content 'Cedar pilot delivery is October 22, 2026.'
```

`carry record correct --id ... --expect-revision ... --event ... --content ...`
is a convenience alias that now creates a **draft correction**. It no longer
publishes a correction immediately. Review and accept it with the proposal
commands. The old low-level `store.supersede` helper remains for compatibility
with C02 callers; it is not the reviewed CLI/MCP path.

The stored target includes source ID, record ID, path, revision and an exact
content digest. Review displays a diff against the target. Acceptance checks
both proposal revision/token and target revision/digest under the shared writer
lock. A competing correction, deleted target, stale revision or external edit
causes a conflict and leaves the proposal unaccepted. An unchanged imported-file
rename is reconciled using its sidecar identity. To rebase a proposal after a
conflict, inspect the current target and create a new proposal event; retries of
the old request are deliberately idempotent.

Corrections replace **the whole target record**, including a whole imported
note. The diff shows that scope. Paragraph-level correction anchors and automatic
recognition of contradictions in unrelated notes are not implemented. A new
accepted decision without a target does not implicitly supersede similar text.

## Canonical history and retrieval

Acceptance commits by atomically changing **one proposal Markdown file**. Its
`carry_target` snapshot and `carry_supersedes` link are authoritative. The target
file stays byte-for-byte intact, including imported files in read-only sources.
There is no second target-file mutation to fail halfway through acceptance.

Carry derives effective `state`, `current` and `superseded_by` from accepted
target links, including across chains. An old file's original frontmatter is a
historical snapshot; readers must resolve these links for its effective current
state. CLI review and recall do this. History retains all dates, IDs and citations.
Deleting the disposable index and rebuilding preserves the relationship.

Normal recall excludes drafts, rejected records and superseded targets **before
ranking**, so a large queue cannot crowd an accepted answer out of the candidate
budget. Pending proposals remain inspectable through `proposal list/show` or the
explicit `recall --drafts` / MCP `include_drafts: true` switch. `--history` includes
superseded evidence; rejected proposals remain in the activity list and source
files, not recall. MCP grounding labels drafts and history as non-current claims.

Recall also checks canonical identities and digests when the index is stale. An
accepted correction hides the old answer even if reindexing failed; the stale
index may report no evidence until the rebuild succeeds. Changed or deleted
files' old indexed bytes are not served as current evidence. If a target is
edited *after* acceptance, Carry stops suppressing the changed source and reports
`correction_target_conflict`. It does not silently treat a changed note as the
snapshot the user approved.

Locks serialize cooperating Carry writers. Content digests detect external
edits seen before commit, including edits made during draft archival. No portable
filesystem API makes a read/check/rename transaction atomic against arbitrary
non-cooperating editors. Power-loss durability of directory metadata is not
claimed. On process interruption, the single canonical acceptance file is either
a draft or accepted; index publication remains atomic and separately observable.

## Optional MCP proposal writes

Explicitly enable each supported client and bind each server process to that
client. This does not edit client settings or enable whole-prompt capture.

```sh
carry --workspace /path/to/state proposal enable --client claude --source records
carry --workspace /path/to/state proposal enable --client codex --source records
carry-mcp --workspace /path/to/state --client claude
# A separate Codex registration uses --client codex (or CARRY_CLIENT=codex).
```

With both conditions satisfied, `tools/list` includes:

```text
carry_propose(content, source_refs, event_id, title?, target_id?,
              target_source_id?, expected_revision?, expected_proposal_revision?)
```

The client supplies a synthesis of its known context and cites source references
as `source_id:relative_path`. References must exist inside configured sources.
For captured events, the client must use the matching event receipt and draft
revision. It refines that event's draft; it cannot claim the other client's
capture event or create a second hook-owned proposal. Non-capture event identities
are namespaced per client. Proposal destinations must be writable personal
sources. Pausing a client's capture also stops its MCP proposal writes.

Clients cannot pass a `client` override in tool arguments. A server without a
bound identity exposes only read tools. Workspace policy is rechecked on every
write; `proposal disable --client CLIENT --source records` revokes it. Restart or
refresh tool discovery after enabling/disabling. There is no MCP accept/reject
operation, and acceptance tokens are obtained through explicit local review.

## Verification

`tests/test_c05_lifecycle.py` adds 32 tests. They cover the complete October
15 → pending October 22 → accepted October 22 → historical October 15 loop,
linked capture synthesis, imported-note replacement without mutation, review
tokens, concurrent corrections, source containment, client gating and revocation,
replay, rejection, stale-index suppression, failed/interrupted acceptance and
fresh stdio clients in both directions.

Actual Claude Code 2.1.267 and Codex CLI 0.153.4 supplied native capture events in
an isolated synthetic workspace. An explicit deterministic test driver supplied
the synthesized decisions over fresh MCP sessions, reviewed the diff and invoked
local acceptance. Both client-bound MCP sessions observed the pending/current/
history transitions. Each native event retained one raw file and one proposal;
replays were idempotent. The test-only hook wrapper stopped the synthetic prompts
before model processing. This validates native capture plus lifecycle/protocol
integration, **not model synthesis or answer-quality evaluation**. Evidence is in
[c05-native-verification.json](c05-native-verification.json).

The full suite has 147 tests: standard Python passes 146 with the optional MCP
SDK test skipped, and the project environment passes all 147. C04's prior changes
are retained. No personal client settings were installed, no publication or push
was performed, and no earlier Ollama performance numbers are claimed as current.


The final wheel was built offline, installed into a clean environment with no
optional dependencies, and tested outside the checkout through the installed
`carry` and `carry-mcp` commands. Proposal creation, invalid review-token refusal,
explicit acceptance, pending correction isolation, automatic indexing, both
client-bound MCP sessions and historical recall passed. See
