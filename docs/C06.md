# C06: packaging spike and local macOS app

Implemented 2026-09-10. Local engineering build; **C06 acceptance remains open
for a pristine macOS install and interactive mouse/keyboard verification**.
The app is not signed/notarized for distribution. Nothing was published or pushed.

## What works

- Native SwiftUI shell on Apple silicon, targeting macOS 14+. An explicit
  standalone CPython 3.13.12 distribution travels inside the `.app`. No system
  Python, Homebrew, pip install, NumPy, PyYAML or MCP SDK is needed at runtime.
- Welcome/create/open workspace, read-only source selection and explicit writable
  destinations. Markdown sources stay separate from the disposable index.
- Overview separates index freshness, provider, pending review, local MCP test,
  capture capability and persisted capture receipts. A local MCP response never
  claims the native client completed trust or captured a prompt.
- Project-local Claude Code and Codex connection previews. Whole-prompt capture
  and client proposals require separate opt-ins. Exact changes, destination,
  client capability and client trust steps appear before Apply.
- Existing unrelated JSON settings survive the merge; Codex TOML comments and
  existing text survive by appending a validated table. Conflicting Carry entries,
  unsupported versions and symlinked settings are refused.
- A durable setup journal precedes writes. Compare-before-write detects changed
  settings. Rollback restores exact prior bytes, including interrupted setup,
  and **refuses any later edit** rather than discarding it. Files created by setup
  can be removed on rollback; empty directories and existing records remain.
- Activity lists drafts, accepted/rejected decisions and effective history, with
  latest capture receipt/failure summaries. Review shows the actual Markdown,
  source links and unified correction diff. Accept/reject uses C05 revision and
  content-token checks; acceptance rebuilds the index and reports pending indexing
  if that fails. Review controls remain visible below a long diff.
- Per-client capture pause also gates that client's proposals. Opening a source
  resolves it against configured roots before asking macOS to open the file.
- Offline lexical retrieval works immediately. The Sources screen links to the
  optional Ollama installation path and explains installing `nomic-embed-text`.
  Carry does not install software or download models automatically.

Unchecked connection opt-ins leave existing opt-ins unchanged. Connection setup
is project-local; `.mcp.json` and `.codex` settings may be versioned with a project,
so the preview explains their scope. Normal personal client settings were not
modified during development or verification.

## Architecture decision and measurements

A native shell with an external Python environment would have a smaller payload
but retain an installation prerequisite. Bundling the relocatable runtime adds
about 49 MB and passed relocation/import/SQLite/MCP checks. No alternate web shell
was implemented or benchmarked; this is a Python-dependency and process-lifecycle
spike, not a claim that SwiftUI outperforms every framework.

The app owns one serialized Python worker over private inherited pipes. There is
no listening socket or HTTP server. This gives the single-owner lifecycle without
an exposed local service. Every command reloads workspace configuration. The app
terminates the worker on normal quit; a closed parent pipe causes EOF and exit.
A failure restarts the core on the next action and never automatically replays a
mutation. Connection previews expire with the worker. A 120-second app deadline
reports failure; after interruption, refresh canonical state before retrying.
Existing CLI/hooks/MCP still use independent short-lived processes and file locks;
Ollama owns the optional embedding model process.

Measured on this development Mac with the frozen 8-note Cedar corpus:

| Measurement | Result |
|---|---:|
| Final app logical file bytes | 49,024,739 (46.75 MiB) |
| Deflated payload estimate | 18,843,246 bytes; excludes symlinks, not a distributable ZIP |
| New Python process + snapshot, p50 / p95, 20 samples | 202.53 / 206.22 ms |
| Existing worker + snapshot, p50 / p95, 40 samples | 2.34 / 3.01 ms |
| Worker lexical recall, p50 / p95, 30 samples | 2.50 / 2.92 ms |
| Worker peak RSS after lexical work | 38,240,256 bytes |
| Installed optional model | 274,302,450 bytes |
| First model probe when not resident, one observation | 852.62 ms |
| Ollama-reported resident model size / VRAM | 370,031,984 bytes / 370,031,984 bytes |
| Worker warm semantic recall, p50 / p95, 30 samples | 19.42 / 30.97 ms |

The process startup difference justifies retaining the app worker for repeated
status/review actions. The model remains optional. Its reported resident size is
not a measurement of total Ollama-process RSS. Model download duration was not
measured because the model already existed. No model was unloaded or downloaded
to manufacture a cold-start result. These are exploratory measurements on one
small corpus, not performance budgets.

Native app startup is measured separately from process launch to SwiftUI
`onAppear`, then to the first workspace response: see
[native startup results](c06-startup-verification.json). This uses 10 new processes
with warm OS caches, not ten rebooted machines. Core timing measurements precede
UI-only error-message changes. Native startup was remeasured after those changes;
the last subsequent edit only made the review footer background opaque.

## Build and reproduce

Use a **relocatable standalone CPython distribution**, not a Homebrew prefix or a
virtual environment. uv-managed Python distributions are suitable. This script
does not download a runtime, add executables to PATH or change the selected Xcode
toolchain. Python used to run the build script must itself have a healthy stdlib.

```sh
python3 scripts/build_macos.py --python-root /path/to/standalone-python \
  --output build/Carry.app
open build/Carry.app

build/Carry.app/Contents/Resources/python/bin/python3 -I -B \
  scripts/prepare_app_demo.py /tmp/new-carry-demo

build/Carry.app/Contents/Resources/python/bin/python3 -I -B \
  scripts/measure_packaging.py build/Carry.app \
  --output /tmp/carry-packaging.json --ollama

build/Carry.app/Contents/Resources/python/bin/python3 -I -B \
  scripts/verify_app_bundle.py --output /tmp/carry-bundle-check.json
```

The output directory must not already exist. Build metadata includes source
SHA-256 values. Keep the application at its chosen location before connecting
clients: settings intentionally pin its interpreter path. Moving the app later
requires reviewing/replacing those connections.

For native view/bridge tests, build a **separate** app with `--view-tests`; this is
a test runner, not the normal user app. Set `CARRY_DESKTOP_WORKSPACE` to a fresh
workspace produced by `prepare_app_demo.py`, and `CARRY_VIEW_TEST_OUTPUT` to a
temporary output directory before launching its `Contents/MacOS/Carry` executable.
It renders real SwiftUI views, accepts the synthetic correction via `Model` and
the actual bundled worker, tests MCP, then restarts the worker. It does not simulate
mouse clicks or automate another application. Test windows render in light mode.

`CARRY_DESKTOP_WORKSPACE` also lets the normal app open a synthetic workspace
without changing its remembered workspace. `CARRY_MEASURE_STARTUP=1` enables two
content-free timing markers, used by `scripts/measure_native_startup.py`.

This machine had two unrelated build-tool issues: Homebrew Python's `plistlib`
import failed due to an expat linkage mismatch, and an obsolete SwiftBridging
module map remained alongside its replacement in Command Line Tools. The build
used standalone Python and `--swift-overlay /tmp/carry-swift-overlay.json` to map
only the obsolete `usr/include/swift/module.modulemap` to an empty temporary file.
The system files were not edited. The optional `--swift-overlay` flag is unnecessary
on a healthy toolchain. The build script does not apply that workaround silently.

## Evidence and remaining gates

- Python suite: **166 tests**. Project environment: all pass. Standard-library
  environment: 165 pass and the optional MCP SDK test skips. Nineteen C06 tests
  cover setup, read-only sources, containment, revision conflicts, rejection,
  worker framing/EOF, settings merge, interruption recovery, rollback conflicts,
  unsupported versions and workspace-bound preview tokens.
- [Dependency and size evidence](c06-packaging-verification.json): copied the app
  to a new path containing spaces, ran outside the checkout with a minimal PATH,
  and verified no optional Python dependencies. SQLite/index/recall/local MCP
  worked. An absent provider returned an explicit unavailable result.
- Wheel and source archive built offline. The wheel installed into a new virtual
  environment without optional packages; desktop imports and a fresh MCP
  initialize/tools/status round trip passed outside the checkout.
- [Bundled connection checks](c06-bundle-verification.json): probed real installed
  Claude Code 2.1.267 and Codex CLI 0.153.4; generated hook commands received
  **synthetic vendor-shaped payloads**, silently persisted once on replay, exposed
  optional MCP proposals, accepted through the app bridge, and persisted nothing
  while paused. This is not new native event-emission evidence. The previous
  actual native-client checks remain in the C04/C05 reports.
- [Native view/bridge results](c06-native-view-verification.json) and local view
  renders verify the app model and worker integration. The computer-use tool
  failed to start its native pipe twice; OS window capture also failed. Interactive
  navigation, native folder panels and actual editor opening were not automated.
  See [overview](c06-overview.png) and [review](c06-review.png) view renders.

**Do not mark the full C06 done-when condition met yet.** A pristine macOS VM or
second machine was not available. macOS 14 minimum-version behavior, a machine
without Ollama/client CLIs, fresh model download duration, Gatekeeper behavior
and interactive setup still need external verification. The dependency-isolated
run is useful evidence, but is not a pristine-machine test.

C07 still owns a signed/notarized pilot installer, broader disconnect/export,
settings migration after app relocation and a setup flow proven with a real user.
Rollback is intentionally conservative: later client edits, including formatting
or Carry pause-policy changes, require review before an old setup can be undone.
Provider installation remains guided, not managed. The app is arm64 only.
